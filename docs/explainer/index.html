Shield Expanded 1.7 guide

Shield Expanded is a mod by FoxMo for RimWorld, a colony simulation game. A mod is an add-on that adds content or code. The Steam Workshop, where players share mods, lists it as item 3575073524. This repo, the project folder under version control, holds a port, a changed copy that runs on RimWorld 1.7 instead of 1.6. This guide covers the mod, how the game loads it, the code, the port's changes, the tests, and what is still open.

What the mod does

Each content group can be switched on or off in the mod settings, after a restart. The Workshop text names three groups.

Shield Buildings & Shield Network adds the Kinetic Shield Generator, the Shield Control Terminal, and the Shield Server Unit. A power grid is the set of buildings that share power through cables, and the buildings on one grid form one shield network. Upgrade points are the units that raise a shield's stats, such as max radius, min radius, charge speed, and max energy. The server unit holds them, and the terminal hands them out.

Shield Equipment adds the ES shield belts, models ES0, ES1, ES2, and ES3. A belt absorbs a ranged hit while it has energy, and each hit costs energy. An empty belt lets the hit through. A worn belt recharges.

Mech Serums adds recipes for the Mech Serum Healer and Mech Serum Resurrector. Both start from an Empty Mech Serum, an intermediate item. Vanilla means the game as it ships, without mods. Biotech is one of the game's expansions, and the serums get their effects from vanilla Biotech, so the tests check only the recipes. The Regenerator series is the other part. It adds injectors that regrow missing body parts.

How RimWorld runs a mod

The game loads a mod in stages. It reads the list of active mods, then the mod's code, then its data. Figure 1 shows the order. These rules come from the game's own code, read with a decompiler on this PC.

XML is a plain text format that marks up data with tags. The game reads the active mod list from Config\ModsConfig.xml in the save data folder. It loads only the listed mods, in list order.

A packageId is the unique ID that tells mods apart. Each mod's About\About.xml holds its name, packageId, supported versions, and required mods. The game lowercases the packageId to match. This mod needs Harmony, a library that changes game methods at run time, so the game's own files stay unchanged. The Harmony mod is item 2009463077 on the Steam Workshop.

LoadFolders.xml has one block per version, such as <v1.7>. The game picks the block that matches its version exactly, or else the newest block not above it. On RimWorld 1.7.5000, the v1.7 block loads, and the port's v1.6 block does not. A slash means the mod's root folder. An entry marked IfModActive loads only while the named mod is active. The folder for Combat Extended, a separate mod that changes combat, uses IfModActive.

A Def is one XML entry that describes one piece of content, such as a building. Defs are the files in a Defs folder that hold these entries. The outer tag names the kind of content, such as ThingDef or HediffDef. An entry marked Abstract is a template, and other entries name it in ParentName.

The mod's code is written in C#, a programming language. A comp is a piece of extra behavior that a Def attaches to a thing. An attribute is a named value inside an XML tag. Class entries in a Def, such as thingClass, hediffClass, and the Class on a comp, name the C# class that the game creates.

An assembly is a compiled code library, saved as a DLL file, which is the Windows format for compiled code. The game loads every DLL in the Assemblies subfolder of each folder it loads. At start-up the game creates each mod's Mod class, and creating that class applies the mod's Harmony patches. For this mod, that class is RimElShrineShieldMod, which builds on RimElShrineMod. RimElShrineMod is abstract, so it serves only as a parent class.

Keyed text is translated text, looked up by key name in Languages folders. English is the fallback language.

How the code is organized

The repo holds four C# projects that matter here. A project is a folder of C# code that builds one DLL file. Harmony patches change game methods, and the core library holds two. A GameComponent is a class that runs for the whole game, not for one object.

ProjectFolderWhat it holds
RimElShrine, the core librarySource\RimElShrine\Settings, the abstract start-up class RimElShrineMod, the two Harmony patches, the compatibility manager, and the ELSClass filter.
RimElShrine.Shields, the shield modSource\RimElShrine.Shields\The start-up class RimElShrineShieldMod, the generator, belt, injectors, and regen effect, and the tuning classes ShieldSetting and MechserumSetting.
RimElShrine.Shields.CE, the Combat Extended projectSource\RimElShrine.Shields.Compatibility\The Combat Extended version of the generator. No game test has run it.
Test mod, in the folder ShieldValidationtools\validation\ShieldValidation\NetworkValidation, EquipmentValidation, and MechSerumValidation, each a GameComponent, plus ValidationSupport.

Both Harmony patches are prefixes, which means they run before the game's own method. The first, on ModSettings.Write, makes this mod save its settings through its own method. The second, on LoadedModManager.ParseAndProcessXML, removes each Def whose ELSClass group is switched off. An ELSClass attribute names that group, such as shield_building. Both patches apply in one call, Harmony.PatchAll, when the mod starts.

The game counts time in ticks. A tick is one step of the game's clock, and 60 ticks make one second. A pawn is any character in the game, such as a colonist. The game calls four kinds of code:

  • The start-up class, once.
  • Comp classes, one for each comp in a Def. The generator's comp is Comp_ShieldNet_ProjInterceptorELS.
  • The hediff class HediffWithComps_LimbsRegen, whose Tick method runs every tick. A hediff is a health condition that the game tracks on a pawn.
  • GameComponent classes. The test mod's checks run from GameComponentUpdate, once per frame.

How each content group works

The shield network

Unless it is stunned, the generator checks the projectiles on the map every tick. The map is one colony's play area. A projectile is a shot or thrown object in flight. The generator must be active. It becomes active when a recharge finishes. It stops being active when a hit uses up its energy, when an EMP hits it, or when its energy drains below zero without power. It intercepts a projectile only when all of these hold:

  • The shot's type is switched on. A ground shot needs InterceptGround. An overhead shot, such as a mortar shell, needs InterceptOverhead.
  • The shot is incoming and InterceptIn is on, or it is outgoing and AllowOut is off. An incoming shot is inside the radius now. A ground shot also started outside the radius, and an overhead shot has its destination inside it. An outgoing shot started inside the radius and is outside it now.
  • If IFFOn is on, the shot's launcher, or the launcher's faction, is hostile to the generator's faction.

These rules come from reading the code. No test has run them in a fight. See Not covered yet. The code is in DoInterception and InterceptProjectile, in Comp_ShieldNet_ProjInterceptorELS.cs.

Each hit costs energy, based on the projectile's damage. If UseKineticEnergy is on, which it is not by default, the cost uses kinetic energy, the energy of motion. The cost is then multiplied by BuildingDmgGlobalFactor. The generator's Def sets isInfiniteEnergy to false, so hits drain its energy. A hit that uses up the energy breaks the shield and turns it off. The generator recharges only while it has power.

The code keeps one ShieldNet for each PowerNet, the game's object for one power grid. Each server unit holds three upgrade points, set by upgradeResources on line 182 of ShieldNet.xml. The Apply button in the terminal's window clears the powered server units, then hands points to them in order. The upgrade value is the bonus the network gives a stat. With no powered terminal, it is 0.

The shield belt

The ES shield belts are worn at the waist. A ranged or explosive hit costs the belt damage × energyLossPerDamage × DmgGlobalFactor. The energyLossPerDamage value is the energy lost for each point of damage. DmgGlobalFactor is a setting that scales that energy cost. The belt absorbs a ranged or explosive hit only while it is worn, its shield is in the Active state, and it has energy. When the shield breaks, it spends a reset period in the Resetting state before it can absorb again. On belts that use blood transfer, the reset can end early by drawing blood from the wearer.

The ES0 belt gains 0.17 energy per second while worn, as set by EnergyShieldRechargeRate in Shields.xml. Its energy stops at 1. The ES3 belt can use blood from its wearer to recharge faster, which causes minor blood loss.

In run 20261107-181001, one ranged hit of 2 damage cost 0.066 energy, which matched the expected value.

The mech serums

An injector is an item that adds the regen effect to a pawn, or ends it. Using one destroys it. The regen effect is the hediff ELS_Hediff_LimbsRegen, which starts at severity 0.1 and can reach 1. Severity is the number that sets how strong a hediff is. An injector that adds the effect also sets a count of heals the effect has left. A Fast injector is a Limited or Forever injector with its Fast flag set.

InjectorWhat it doesCountFast
CleanerEnds a running regen effectNot usedNo
LimitedAdds the regen effect3No
ForeverAdds the regen effectNoneNo
Fast LimitedAdds the regen effect3Yes
Fast ForeverAdds the regen effectNoneYes

The regen clock gains 0.5 seconds every 30 ticks. A missing part heals once the clock passes its cost, which is the part's max health times 60 seconds. Max health is the health a body part has when whole. A finger has max health 8, so the cost is 480 seconds. The clock must pass 480, which takes 961 steps of 0.5 seconds. Counted from the first tick of regrowth, the first step comes at tick 32 and the rest follow every 30 ticks. The finger therefore heals at tick 28,833, not at the 28,800 that 480 seconds at 60 ticks a second would give. The check window is 23,040 to 31,680 ticks.

Each heal lowers the count by one. At zero, the effect ends. An effect with no count does not end from heals.

Blood loss is the health condition that tracks how much blood a pawn has lost. Quick regen is a faster mode of the regen effect. It starts when severity is above 0.5. In the 1.7 build, a Fast injector sets severity to 1, so its effect starts in quick regen. The 1.6 build never reads the Fast flag, so a Fast injector does nothing extra there.

In quick regen, the clock gains 1.5 seconds every 30 ticks, three times the normal speed, while the extra time applies. The setting QuickRegenFactor sets that speed, and it defaults to 3. Each step adds blood loss equal to the extra seconds divided by LimbsRegenSecondsPerHealth, times QuickRegenBloodLossPercentPerHealth, which defaults to 0.005. The extra time applies only while the pawn's blood loss is below QuickRegenBloodLossMax, which defaults to 0.35, and only when the next step's blood loss still fits under that cap. Otherwise the part regrows at normal speed, so a pawn with no blood loss gets no extra time.

How the tests prove the mod works

A validation run is a test run that checks the mod inside the game. The runner, tools\validation\Invoke-Scenarios.ps1, is a PowerShell script, which is Windows' built-in scripting tool. It starts RimWorld headless, meaning with no window, and loads the port and a test mod. The test mod's folder is ShieldValidation, and its package ID is local.shields17.validation.

The runner refuses to start while RimWorld runs. It builds the test mod, writes ModsConfig.xml and Prefs.xml into the run's own Config folder, and makes two junctions in the game's Mods folder. A junction is a Windows folder link that makes one folder appear at a second path. The runner starts the game with its own save data folder and waits up to 300 seconds. Then it copies Player.log, the game's log file, removes the junctions, and checks the results.

Three GameComponents run the checks inside the game. Each check writes one row to validation-results.txt and to the game log, marked [ShieldValidation]. A row is one check result. Each group also writes a completion row, which reads finished.

A run passes only when:

  • Every required scenario row reads PASS, and every group completion row reads finished.
  • The log has one [ShieldValidation] marker for each row. The runner compares the counts, not the text of each marker.
  • No other RimWorld process ran during the run.
  • The mod list has the port and the test mod, with no notes.
  • The log has no error line that mentions the port or the test mod.

The runner checks only the rows named in its two lists. A failing row that the lists do not name does not fail the run.

A control run turns one part off on purpose, so its checks must fail. The switches are -shieldvalidation-nopower, -shieldvalidation-nowear, and -shieldvalidation-noserum. Run 20261107-180127 used the last one. It fails the six mech rows that need serum, and it passes the recipe row and the network and equipment rows, as designed.

The project's rule is to reproduce a bug red in a run before fixing it. Three runs failed before the fix commit. Runs 20261107-174532 and 20261107-174938 failed the bleeding-pawn row. Run 20261107-175322 passed that row and failed the healthy-pawn row. Run 20261107-181001 passes both.

Only one RimWorld session runs at a time, per ADR 0010. Every session writes the same Player.log, so overlapping sessions mix their lines. An overlapping run is not valid evidence, even when it reads PASS. A separate watcher outside this repo waits two quiet minutes before a run starts.

The mech group steps the game one tick at a time, in its own loop. The game ignores speed changes made before the player has control, which is the case at a new colony's first tick. Without the loop, a finger would take about 8 minutes of real time to regrow at normal speed.

Not covered yet

Five areas are not covered yet:

  • Combat interception, meaning a shield that stops real projectiles in a fight.
  • The Combat Extended path. Nothing has run in the game yet.
  • The Healer and Resurrector effects. Only their recipes are checked.
  • The Steam Workshop upload. Upload as Private first, then switch to Public after the owner tests it. Before any upload, check RimElShrine.Shields\About\PublishedFileId.txt. It holds 3575073524, the original mod's Workshop item number.
  • The player's path to use an injector. The Fast rows call the injector's DoEffect method directly. That skips the usability check, which can clear blood loss, as decision D4 describes.

Open decisions

Lucas decides these two open choices. Neither blocks the work, and each default applies if the owner does not answer.

D3. How the test clock runs

A finger takes 28,833 ticks to regrow, which is about 8 minutes at normal speed. The harness moves the game forward itself, one tick at a time. The other option is to let the game run at its fastest speed once the colony is ready. Its speed has not been measured here, and it needs one more full run to prove it works. The default is to keep the loop. No work waits.

D4. Whether the usability check cures a bleed

The usability check, CanBeUsedBy, calls the port's TryGetHediff helper for the regen effect. With no regen effect, the helper sets the pawn's blood loss to zero. So checking a bleeding pawn can cure its bleed. The 1.6 build makes the same call.

The options are to leave it in both builds, to fix it in the 1.7 build only, or to fix it in both. Fixing the 1.6 code changes FoxMo's build the next time someone builds it. The default is to leave it in both builds. No work waits.

Answered decisions

D1. Fast injectors work only while a pawn has blood loss. The owner answered on 2026-11-07, as ADR 0011 records.

D2. The target is the installed build, RimWorld 1.7.5000 rev1275. The owner chose it on 2026-11-07, as ADR 0002 records.
